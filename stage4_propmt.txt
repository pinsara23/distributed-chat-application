# 6. Part A — Distributed User Presence

Stage 2 kept WebSocket connections locally.

For example:

```text
Server 1:
Alice

Server 2:
Charlie

Server 3:
Bob
```

That is still correct.

However, we now want every server to be able to determine whether a user is approximately:

```text
online
offline
```

without sharing Python memory.

Use Redis for distributed presence.

---

# 7. Redis Presence Model

Use Redis keys representing connected users.

For example:

```text
presence:user:12
```

Possible value:

```json
{
  "server_id": "chat-server-3",
  "connection_id": "uuid"
}
```

The key should have a TTL.

Conceptually:

```text
presence:user:12
TTL = 30 seconds
```

The exact TTL can be configurable.

Do NOT permanently store online status without expiration.

Otherwise a crashed server could leave users appearing online forever.

---

# 8. Why TTL Matters

Suppose Bob is connected to Server 3.

Redis contains:

```text
presence:user:12 = server-3
```

Then Server 3 crashes.

It cannot execute:

```text
delete presence:user:12
```

because it is dead.

Without TTL:

```text
Bob = online forever
```

With TTL:

```text
Server crashes
      ↓
heartbeat stops
      ↓
TTL decreases
      ↓
key expires
      ↓
Bob becomes offline
```

This is a basic failure-detection mechanism.

---

# 9. Heartbeats

While a WebSocket connection is active, refresh the user's presence TTL periodically.

Conceptually:

```text
Client connected
      │
      ▼
presence:user:12
TTL 30 sec
      │
      ▼
heartbeat
      │
      ▼
TTL refreshed
```

For example:

```text
Heartbeat interval = 10 seconds
Presence TTL = 30 seconds
```

Make values configurable.

Do not hardcode timing throughout the application.

---

# 10. Presence Lifecycle

Expected lifecycle:

## Connect

```text
WebSocket authenticated
        ↓
connection registered locally
        ↓
Redis presence created
```

## Active

```text
heartbeat
    ↓
presence TTL refreshed
```

## Clean Disconnect

```text
WebSocket closes
      ↓
local connection removed
      ↓
presence removed/updated
```

## Server Crash

```text
No cleanup possible
      ↓
heartbeat stops
      ↓
TTL expires
      ↓
presence disappears
```

# 14. Part B — WebSocket Heartbeat / Liveness

Presence TTL and WebSocket liveness are related but should be understood separately.

Implement an application heartbeat or WebSocket ping/pong strategy appropriate for the selected WebSocket stack.

Purpose:

```text
Detect dead/stale connection
        ↓
clean local state
        ↓
stop presence refresh
```

Do not rely indefinitely on a socket that appears open in memory.

# 15. Part C — Client Reconnection

Network connections fail.

Examples:

```text
Wi-Fi temporarily drops
Laptop sleeps
Server restarts
Nginx reconnect occurs
Container restarts
```

The client should reconnect automatically.

Implement a reference/test client that demonstrates this behavior.

Use bounded exponential backoff with jitter conceptually:

```text
disconnect
   ↓
wait
   ↓
reconnect attempt
   ↓
failure
   ↓
wait longer
   ↓
reconnect
```

Do not use an aggressive infinite loop such as:

```text
while disconnected:
    reconnect immediately
```

That can create a reconnection storm.

---

# 16. Reconnection Authentication

Every new WebSocket connection must be authenticated again.

Do not assume:

```text
This socket used to belong to Alice,
therefore the new socket is Alice.
```

The replacement connection must provide valid authentication.

Expired JWTs must be handled appropriately.

---

# 17. Part D — Message Synchronization After Reconnect

Reconnecting a WebSocket is not enough.

Messages may have been created while the client was disconnected.

Therefore implement message synchronization.

Example:

```text
Bob received message 100
        ↓
Bob disconnects
        ↓
messages 101, 102, 103 created
        ↓
Bob reconnects
        ↓
fetch messages after 100
```

This is an important recovery mechanism.

---

# 18. Synchronization Cursor

Use a stable cursor.

Possible approaches:

```text
message sequence
message UUID + ordering information
created_at + tie-breaker
database primary key
```

Prefer an unambiguous ordering mechanism.

For a simple system, a monotonically increasing database message ID can be used for synchronization while UUID remains the globally stable logical identifier.

Example:

```text
GET /conversations/15/messages?after_id=100
```

Then return:

```text
101
102
103
```

Do not rely only on client clocks.

---

# 19. Real-Time + History Must Converge

The application should be correct even if a real-time event is missed.

Important principle:

```text
WebSocket
=
low-latency delivery

PostgreSQL history
=
recovery/source of truth
```

If Bob misses a WebSocket event, synchronization after reconnect should recover the message from PostgreSQL.

---

# 20. Duplicate Recovery

A race can happen:

```text
Bob reconnects
      ↓
fetches missed messages
      ↓
same message also arrives over WebSocket
```

The client should use stable message UUIDs to deduplicate.

Conceptually:

```text
if message_id already processed:
    ignore duplicate
```

This continues the idempotency ideas learned in Stage 3.

---

# 21. Part E — Graceful Server Shutdown

When a FastAPI server intentionally shuts down:

- stop accepting new work
- cancel/finish background tasks appropriately
- close RabbitMQ resources
- close Redis resources
- close database resources where applicable
- clean local WebSocket state
- stop presence heartbeats
- close WebSockets cleanly where practical

Use FastAPI lifespan management.

Do not simply terminate background tasks without understanding cleanup.

---

# 22. Server Failure

There are two cases.

## Graceful Shutdown

The application knows it is stopping and can clean up.

## Crash

The process suddenly disappears.

It cannot clean up.

Therefore distributed state must not depend entirely on graceful cleanup.

This is why presence uses:

```text
TTL + heartbeat
```

instead of only:

```text
delete key on disconnect
```

---

# 23. Nginx Failure Handling

Configure Nginx so unhealthy/unavailable backend instances are not continuously treated as usable.

For normal HTTP traffic, requests should be able to reach remaining healthy instances.

Example:

```text
Server 2 fails

Server 1 ✓
Server 2 ✗
Server 3 ✓
```

New connections should still be able to use available servers.

Existing WebSockets connected to Server 2 will break and clients must reconnect.

Do not claim Nginx can magically migrate an existing TCP/WebSocket connection to another backend.

It cannot.

Recovery happens by reconnecting.

# 26. Redis Failure

Redis currently supports:

```text
real-time cross-server events
presence
```

If Redis temporarily fails:

- presence information may become unavailable/stale
- real-time delivery may be disrupted
- durable chat messages should remain protected by PostgreSQL/RabbitMQ/outbox mechanisms

Do not report users as definitely offline merely because Redis is unavailable.

```text

```

```text

```

# 27. RabbitMQ Failure

Stage 3 transactional outbox should help.

If RabbitMQ fails:

```text
message transaction
     ↓
PostgreSQL
     ↓

```

When RabbitMQ returns:

```text
outbox publisher
      ↓
publish pending events
```

Verify this behavior in Stage 4 fault tests.

# 28. PostgreSQL Failure

PostgreSQL is the persistent source of truth.

If it is unavailable, operations requiring durable message creation should fail safely.

Do NOT pretend a message was successfully stored when it was not.

Do not silently acknowledge successful message creation if the transaction failed.

# 29. Part F — End-to-End Encryption

Stage 3 implemented **server-side application encryption**.

Conceptually:

```text
Alice
  │ plaintext
  ▼
Server
  │ encrypt
  ▼
Database ciphertext
```

The server possesses the key.

Therefore the server can decrypt messages.

That is NOT E2EE.

Stage 4 should change the architecture.

---

# 30. E2EE Goal

With end-to-end encryption:

```text
Alice Device
     │
     │ Encrypt locally
     ▼
Ciphertext
     │
     ▼
Server
     │
     ▼
Database
     │
     ▼
RabbitMQ
     │
     ▼
Bob Device
     │
     │ Decrypt locally
     ▼
Plaintext
```

The backend should not require plaintext to route/store ordinary E2EE chat messages.

---

# 31. Important E2EE Principle

The encryption key required to decrypt conversation content should not simply be a global server-side secret.

Otherwise it is still server-side encryption.

Conceptually:

```text
Stage 3:

Server has message encryption key
```

Stage 4:

```text
Alice endpoint ── cryptographic relationship ── Bob endpoint

Server transports ciphertext
```

---

# 32. Do Not Invent Cryptography

This requirement is critical.

Do NOT create:

```text
my_custom_encrypt()
XOR encryption
custom Diffie-Hellman protocol
custom ratchet
custom cipher
home-made authentication scheme
```

Use established cryptographic primitives through maintained libraries.

The educational implementation should clearly state its security scope and limitations.

---

# 33. E2EE Scope for This Project

Do not attempt to recreate the entire Signal Protocol from scratch.

That would massively increase project complexity and security risk.

For this educational Stage 4, implement a **limited, clearly documented E2EE design for one-to-one chat** using established library primitives.

It should demonstrate:

- client-side key generation
- public-key distribution
- authenticated key agreement
- conversation/session key derivation
- authenticated encryption
- ciphertext transport
- client-side decryption
- key identity verification concept
- key rotation/versioning concept

It should NOT claim to provide all properties of Signal, WhatsApp, or another production messenger.

---

# 34. Client-Side Key Pairs

Each user/client should generate cryptographic key material on the client side.

Conceptually:

```text
Alice
├── private key
└── public key

Bob
├── private key
└── public key
```

The private key must remain on the client.

The server may store/distribute the public key.

Do not send raw private keys to the server.

---

# 35. Public-Key Directory

The backend may expose authenticated endpoints for public keys.

Conceptually:

```text
POST /keys/public
GET /users/{id}/keys
```

The exact API can differ.

The server stores:

```text
user_id
public_key
key_version
created_at
```

The server must NOT store the corresponding plaintext private key.

---

# 36. Key Agreement

Use an established key-agreement primitive supported by the selected cryptographic library.

A modern elliptic-curve Diffie-Hellman construction such as X25519 is appropriate for an educational implementation when correctly used through a trusted library.

Conceptually:

```text
Alice private key
      +
Bob public key
      ↓
shared secret
```

Bob performs:

```text
Bob private key
      +
Alice public key
      ↓
same shared secret
```

The raw shared secret should be passed through an appropriate standard key-derivation function according to the library/design rather than directly treated as arbitrary encryption material.

Do not implement elliptic-curve mathematics manually.

---

# 37. Authenticated Encryption

Use a standard AEAD construction supported by the selected library.

For example:

```text
AES-GCM
```

or another suitable established AEAD.

The selected design should provide:

```text
confidentiality
+
integrity/authentication
```

Follow the library's nonce requirements exactly.

Never intentionally reuse a nonce with the same key when prohibited.

---

# 38. E2EE Message Format

The server should handle an encrypted envelope approximately like:

```json
{
  "message_id": "uuid",
  "conversation_id": 15,
  "sender_id": 7,
  "key_version": 2,
  "ciphertext": "...",
  "nonce": "...",
  "created_at": "..."
}
```

Do not send:

```text
plaintext
private key
shared secret
```

to the backend.

The exact envelope depends on the selected library and E2EE design.

---

# 39. Associated Data

If the selected AEAD supports associated authenticated data, consider binding important non-secret metadata such as:

```text
message_id
conversation_id
sender identity
protocol version
```

to the ciphertext.

Explain why authenticated metadata can help prevent ciphertext being validly moved into an unintended context.

Use one canonical serialization format so both endpoints authenticate exactly the same bytes.

---

# 40. Key Identity Verification

A public-key server creates an important trust issue:

```text
How does Alice know the key returned for Bob really belongs to Bob?
```

Do not ignore this.

For this educational project, implement or document a key fingerprint verification mechanism.

Example concept:

```text
Bob key fingerprint:
AB12 CD34 EF56 ...
```

Alice and Bob can compare fingerprints through another trusted channel.

The UI/reference client may expose:

```text
View security fingerprint
```

Do not claim that simply downloading a public key from the server completely solves identity authentication.

---

# 41. Key Change Handling

If Bob's public identity key changes unexpectedly, the client should not silently treat that as meaningless.

Possible behavior:

```text
Security key changed for Bob.
Verify the new fingerprint before continuing sensitive communication.
```

For this educational project, at minimum:

- detect key version/change
- store known peer fingerprint locally
- surface the change
- explain the security significance

---

# 42. Key Versioning

Public keys should have versions.

Example:

```text
user_id = 12
key_version = 3
```

Encrypted messages should identify the key/session version required for interpretation.

This helps support future key rotation.

---

# 43. Private Key Storage

Private keys must remain client-side.

For the reference development client, store them in the safest practical local mechanism available to the implementation.

Do not:

```text
commit private keys to Git
hardcode private keys
log private keys
send private keys to FastAPI
store them in PostgreSQL as plaintext
```

Explain that production mobile/desktop applications should use OS-backed secure key storage where available.

---

# 44. Stage 3 Encryption Migration

Stage 3 stored server-encrypted messages.

Stage 4 introduces E2EE.

Do not silently destroy old messages.

Use encryption/protocol versioning.

For example:

```text
encryption_mode
```

could conceptually distinguish:

```text
server_encrypted_v1
e2ee_v1
```

or use a protocol/version field appropriate to the existing schema.

Existing Stage 3 messages can continue using the previous authorized server-decryption path while new Stage 4 messages use E2EE.

Explain migration limitations clearly.

# 45. Backend Changes for E2EE

The backend should stop expecting message plaintext for new E2EE messages.

Instead of:

```json
{
  "content": "Hello Bob!"
}
```

the client sends something conceptually like:

```json
{
  "ciphertext": "...",
  "nonce": "...",
```

The backend still performs:

- conversation authorization
- sender validation
- recipient/conversation validation
- message ID handling

- RabbitMQ event creation
- routing
- delivery

But it does not need the plaintext.

# 60. Important Distributed Systems Concepts Learned Across All Four Stages

By finishing Stage 4, I should understand:

### Horizontal Scaling

Multiple application instances.

### Load Balancing

Traffic distributed between servers.

### Shared Persistent State

PostgreSQL shared by application instances.

### Local State

WebSocket connection belongs to one process/server.

### Pub/Sub

Fast cross-server notification.

### Message Broker

Reliable asynchronous work distribution.

### ACK/NACK

Processing acknowledgement.

### At-Least-Once Processing

Events may be redelivered.

### Idempotency

Duplicate events should not cause duplicate business effects.

### Retry

Temporary failures can recover.

### Dead-Letter Queue

Repeatedly failing events are isolated.

### Dual-Write Problem

Database and broker cannot naively be treated as one atomic operation.

### Transactional Outbox

Persistent event publication bridge.

### Heartbeats

Repeated liveness indication.

### TTL

Automatically expires stale distributed state.

### Presence

Distributed ephemeral user state.

### Failure Detection

Determining that connections/services may no longer be available.

### Reconnection

Recovering network sessions.

### Synchronization

Recovering messages missed during disconnection.

### Eventual Consistency

Different parts of the system may temporarily have different views but converge.

### Fault Tolerance

Continuing/recovering when individual components fail.

### Server-Side Encryption

Server controls decryption.

### End-to-End Encryption

Endpoints control message confidentiality.
