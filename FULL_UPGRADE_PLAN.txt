4. Existing Message Lifecycle
-----------------------------

Client encrypts message
        |
        v
WebSocket receives ciphertext
        |
        v
FastAPI validates JWT
        |
        v
PostgreSQL stores message and outbox event
        |
        v
Outbox publisher sends event to RabbitMQ
        |
        v
RabbitMQ consumer retrieves message from PostgreSQL
        |
        v
Consumer publishes ciphertext to Redis
        |
        v
FastAPI instance holding recipient WebSocket receives event
        |
        v
Recipient decrypts message locally

Current lifecycle problems:

1. WebSocket sender authorization is incomplete.
2. Conversation membership is not verified.
3. Duplicate client submissions are not prevented.
4. Outbox publication can race across replicas.
5. Redis Pub/Sub is not durable.
6. Reconnect does not automatically replay missed messages.
7. Message ordering is not guaranteed.
8. Sender and recipient delivery semantics are not explicitly modeled.


5. Critical Backend Changes
---------------------------

Priority 0 - Security and correctness

5.1 Secure WebSocket authorization

Affected files:

app/websocket/chat.py
app/services/chat_service.py

Add a service method that verifies:

- Sender belongs to the conversation.
- Target belongs to the conversation.
- Conversation exists.
- Target user exists.

The check must happen before inserting the message.

Expected behavior:

- Return a WebSocket authorization error.
- Do not insert a database message.
- Do not create an outbox event.
- Do not publish to Redis.

The WebSocket must not trust only conversation_id and target_user_id supplied
by the client.

5.2 Secure message history authorization

Affected files:

app/api/conversations.py
app/services/chat_service.py

Both normal pagination and after_id retrieval must verify that the
authenticated user belongs to the conversation.

5.3 Fix migration consistency

Affected files:

alembic/versions/
app/models/outbox_events.py
app/messaging/rabbitmq/publisher.py

Do not edit an already-applied migration. Create a new corrective migration
that:

1. Detects publised_at.
2. Renames it to published_at.
3. Preserves existing data.
4. Verifies the final schema.

The migration must be tested against a real PostgreSQL database.

5.4 Fix encrypted message serialization

Affected files:

app/api/conversations.py
app/websocket/chat.py
app/messaging/rabbitmq/consumer.py
app/schemas/message.py
app/models/message.py

Use one consistent format:

Database: bytes
API/WebSocket: Base64 string
Client: Base64 string

Use Base64 encoding for binary message fields. Never decode arbitrary
ciphertext bytes as UTF-8.

5.5 Standardize protocol naming

The existing field is cipertext. Do not silently rename it.

Recommended compatibility approach:

Protocol v1:
    cipertext

Protocol v2:
    ciphertext

During migration:

- Accept both fields.
- Prefer ciphertext.
- Emit the negotiated protocol field.
- Eventually deprecate cipertext.

Apply the same approach to key_version and encryption_version.


6. Conversation Improvements
----------------------------

The frontend should search for a user and call:

POST /conversations/

The backend should return an existing direct conversation or create one.

Duplicate-conversation prevention:

Affected files:

app/models/conversation.py

Recommended design:

A database constraint is required because application-level checks alone are
not safe under concurrency.

9. Outbox Reliability Plan
--------------------------

Current problem:

Every FastAPI replica runs an outbox publisher. Without row claiming:

Server 1 reads event A
Server 2 reads event A
Server 3 reads event A
All publish event A

Required outbox fields:

- published_at
- claimed_at
- claim_owner
- attempt_count
- last_error

Required behavior:

1. Claim a bounded batch.
2. Publish events.
3. Use RabbitMQ publisher confirms.
4. Mark successful events as published.
5. Increment retry state on failure.
6. Release or expire abandoned claims.

Use SELECT FOR UPDATE SKIP LOCKED or an equivalent leasing mechanism.

Affected files:

app/models/outbox_events.py
app/messaging/rabbitmq/publisher.py
alembic/versions/<outbox_claiming_migration>.py


10. Duplicate Processing and Idempotency
----------------------------------------

Current consumer behavior:

exists(key)
process event
set(key)

Two consumers can pass the exists() check at the same time.

Use an atomic Redis operation:

SET processed_event:<event_id> 1 NX EX 86400

Only the consumer that successfully creates the key should process the
event.

A safer state model is:

processing
completed

Another option is storing processed events in PostgreSQL with a unique
event_id and performing the check transactionally.

Affected files:

app/messaging/rabbitmq/consumer.py
tests/test_stage3.py


11. RabbitMQ Retry Improvements
-------------------------------

Recommended retry policy:

Transient infrastructure error:
    retry

Malformed event:
    dead-letter immediately

Missing message row:
    retry briefly, then dead-letter

Invalid target:
    dead-letter

Permanent schema error:
    dead-letter and alert

Do not treat every exception as retryable.

Add event_id, retry_count, and last_error to structured logs.

Affected files:

app/messaging/rabbitmq/consumer.py
app/messaging/rabbitmq/connection.py
tests/test_stage3.py

13. WebSocket Connection Management
------------------------------------

Current design:

This creates a race when the same user connects from multiple tabs or
devices.

Recommended structure:

dict[user_id, dict[connection_id, WebSocket]]

Each connection should have:

- connection_id
- user_id
- created_at
- last_seen_at

Disconnect should remove only the specific connection that closed.

Presence should remain online while at least one active connection exists.

Affected files:

14. Message Ordering
--------------------

The current system does not guarantee strict ordering.

Recommended approach:

- Use database id or a server-generated sequence per conversation.
- Return message_id and created_at.
- Order history by (created_at, id).
- Use id as the deterministic tie-breaker.
- Add client-side duplicate filtering.
- Do not rely only on timestamps.

Recommended message envelope:

{
  "message_uuid": "...",
  "sequence": 123,
  "conversation_id": 1,
  "sender_id": 1,
  "created_at": "...",
  "ciphertext": "...",
  "nonce": "...",
  "protocol_version": 2
}


15. Offline Recovery and Reconnection
-------------------------------------

The browser should store the last received message ID per conversation.

After reconnecting:

1. Authenticate again.
2. Re-establish the WebSocket.
3. Request missed messages.
4. Insert messages in sequence order.
5. Deduplicate by message_uuid.
6. Resume real-time delivery.

Recommended endpoint behavior:

GET /conversations/{id}/messages?after_id=100&limit=100

Response:

{
  "messages": [],
  "has_more": false,
  "next_after_id": 150
}

16. E2EE Compatibility Plan
---------------------------

The Python clients currently use:

- X25519
- PEM public keys
- HKDF-SHA256
- HKDF info: distributed-chat-e2ee-v1
- AES-GCM
- 12-byte random nonce
- Base64 ciphertext
- Base64 nonce
- Server-stored public keys
- TOFU fingerprints

The browser implementation must preserve these exact parameters for
compatibility.

Browser implementation options:

Option A - Web Crypto:

Use native browser APIs if the selected browser targets support the required
X25519, HKDF, AES-GCM, and SPKI operations.

Option B - libsodium:

Use a maintained browser-compatible library for exact X25519 compatibility.
Key format conversion must be verified.

Option C - Noble cryptography library:

Use a maintained TypeScript library only after verifying that its X25519,
HKDF, and AES-GCM outputs match the Python implementation.

Required compatibility tests:

- Public-key import and export
- Fingerprint generation
- Shared-key derivation
- HKDF output
- AES-GCM encryption and decryption
- Nonce encoding
- Ciphertext encoding
- Tamper detection
- Wrong-key rejection

Do not silently change:

- Cryptographic algorithms
- Key formats
- HKDF info
- Nonce size
- Ciphertext format
- Field names
- Key-version semantics

If changes are necessary, introduce:

- protocol_version
- encryption_version
- key_version

and support both protocol versions during migration.

Browser key storage should use IndexedDB and non-extractable CryptoKey where
possible. Avoid localStorage and plain JSON private-key storage.

Affected files:

client/crypto.py
client_bob/crypto.py
app/api/keys.py
app/services/key_service.py
app/schemas/key.py
new frontend encryption modules
new E2EE compatibility tests

23. Final Recommendation
------------------------

The existing distributed architecture is suitable and should not be replaced.

The highest-priority work is:
