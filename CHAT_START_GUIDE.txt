Distributed Chat - Two-User Startup Guide
==========================================

This guide starts the Docker services, creates two users through Postman,
creates a conversation, and runs the two encrypted terminal clients.


1. Start the Docker services
----------------------------

On the server machine, open a terminal in the project directory:

    cd ~/distributed-chat-application

Check that the Compose file is valid:

    sudo docker compose config

Start or recreate the services:

    sudo docker compose up -d --force-recreate

Check the service status:

    sudo docker compose ps

Check the API:

    curl http://localhost/health/live
    curl http://localhost/health/ready

If this is a fresh database, run the migrations before registering users.
The published chat image does not include the Alembic migration directory,
so run Alembic from the repository on the Docker server:

    sudo apt update
    sudo apt install -y python3-venv
    python3 -m venv .venv
    source .venv/bin/activate
    python -m pip install -r requirements.txt

Before running Alembic, confirm that both migration files are present:

    ls -la alembic.ini alembic

If either path is missing, update the repository checkout or copy the
tracked migration files from the project source:

    git pull

Do not run "alembic init" for this project. The existing migration history
under alembic/versions is required to create the complete database schema.

Use the PostgreSQL port published by Docker. Replace YOUR_POSTGRES_PASSWORD
with the value from .env:

    export DATABASE_URL="postgresql+asyncpg://admin:YOUR_POSTGRES_PASSWORD@localhost:5432/chat_db"
    export SYNC_DATABASE_URL="postgresql://admin:YOUR_POSTGRES_PASSWORD@localhost:5432/chat_db"
    alembic upgrade head

Do not use sudo with the alembic command while the virtual environment is
active. If the database password contains characters such as @, :, /, or #,
URL-encode those characters in the connection URL.

Confirm that the tables exist:

    sudo docker compose exec postgres psql -U admin -d chat_db -c '\dt'

Run the Docker services again if necessary:

    sudo docker compose restart chat_server_1 chat_server_2 chat_server_3

From another computer on the same network, use the server IP:

    http://192.168.43.47/docs

Replace 192.168.43.47 with the actual server IP if it changes.


2. Create two users in Postman
------------------------------

Create a Postman environment variable:

    base_url = http://192.168.43.47

Use http://localhost instead when Postman is running on the Docker server.


Register User 1 (Alice)
-----------------------

Request:

    POST {{base_url}}/auth/register

Headers:

    Content-Type: application/json

Body -> raw -> JSON:

    {
      "username": "alice",
      "email": "alice@example.com",
      "password": "AlicePass123!"
    }

Send the request and record the returned id. This is Alice's user_id.


Register User 2 (Bob)
---------------------

Request:

    POST {{base_url}}/auth/register

Headers:

    Content-Type: application/json

Body -> raw -> JSON:

    {
      "username": "bob",
      "email": "bob@example.com",
      "password": "BobPass123!"
    }

Send the request and record the returned id. This is Bob's user_id.

Do not assume the IDs are 1 and 2 if users already exist. Use the IDs
returned by the registration responses.


3. Login both users in Postman
------------------------------

Login Alice:

    POST {{base_url}}/auth/login

Body -> x-www-form-urlencoded:

    username = alice
    password = AlicePass123!

The response contains:

    {
      "access_token": "...",
      "token_type": "bearer"
    }

Save Alice's access_token.

Login Bob using another request:

    POST {{base_url}}/auth/login

Body -> x-www-form-urlencoded:

    username = bob
    password = BobPass123!

Save Bob's access_token.

Important: Login uses x-www-form-urlencoded, not JSON.


4. Create a conversation
------------------------

Use Alice's token to create a conversation with Bob.

Request:

    POST {{base_url}}/conversations/

Headers:

    Authorization: Bearer ALICE_ACCESS_TOKEN
    Content-Type: application/json

Body -> raw -> JSON:

    {
      "user_id": 2
    }

Replace 2 with Bob's actual user_id.

The response contains the conversation id:

    {
      "id": 1,
      "created_at": "..."
    }

Save this conversation id. Both clients must use the same id.


5. Configure client/main.py for Alice
--------------------------------------

Open:

    client/main.py

Update the configuration near the top:

    TOKEN = "ALICE_ACCESS_TOKEN"
    USER_ID = ALICE_USER_ID
    TARGET_USER_ID = BOB_USER_ID
    CONVERSATION_ID = CONVERSATION_ID

For a client running on another computer, use the server IP:

    REST_URL = "http://192.168.43.47"
    WS_URL = f"ws://192.168.43.47/ws/chat?token={TOKEN}"

For a client running on the Docker server itself, use:

    REST_URL = "http://localhost"
    WS_URL = f"ws://localhost/ws/chat?token={TOKEN}"

Run Alice from the client directory so her private key and known_hosts file
stay separate from Bob's:

    cd client

Do not copy Bob's private key files into Alice's directory.


6. Configure client_bob/main.py for Bob
----------------------------------------

Open:

    client_bob/main.py

Update:

    TOKEN = "BOB_ACCESS_TOKEN"
    USER_ID = BOB_USER_ID
    TARGET_USER_ID = ALICE_USER_ID
    CONVERSATION_ID = CONVERSATION_ID

Use the same REST_URL and WS_URL server address as Alice:

    REST_URL = "http://192.168.43.47"
    WS_URL = f"ws://192.168.43.47/ws/chat?token={TOKEN}"

Bob must use Bob's token and Bob's user_id. Do not use Alice's token
in client_bob/main.py.

Run Bob from the client_bob directory so his private key and known_hosts
file stay separate from Alice's:

    cd client_bob


7. Install and run the clients
------------------------------

On each client machine, install Python 3.11 or newer and the client
dependencies:

    python -m pip install -r client/requirements.txt
    python -m pip install -r client_bob/requirements.txt

Run Alice in one terminal:

    cd client
    python main.py

Run Bob in a second terminal:

    cd client_bob
    python main.py

The clients register their public keys automatically. On the first
connection, each client may display the peer fingerprint and save it in
its known_hosts file. Verify the fingerprint before trusting it.

Type a message in either terminal and press Enter. Messages are encrypted
by the client before being sent through the WebSocket.


8. Troubleshooting
------------------

Check application logs:

    sudo docker compose logs --tail=100 chat_server_1
    sudo docker compose logs --tail=100 chat_server_2
    sudo docker compose logs --tail=100 chat_server_3
    sudo docker compose logs --tail=100 nginx

If you receive 502 Bad Gateway, check that all chat_server containers are
running. A 502 normally means Nginx cannot reach an application server.

If a client cannot connect, verify:

    - The server IP is correct.
    - Port 80 is allowed through the server firewall.
    - The client uses ws://, not http://, for WS_URL.
    - The token has not expired.
    - USER_ID, TARGET_USER_ID, and CONVERSATION_ID are correct.

Never commit real JWT tokens, passwords, private keys, or the .env file.
