1. The Distributed-Systems Problem (Poison Messages)

Currently, if our consumer crashes while processing a message 
(e.g., Redis is temporarily down), 
it hits the except Exception block and triggers await message.nack(requeue=False). 
That deletes the message forever.

If we change it to requeue=True, RabbitMQ will instantly shove it back to the front of the queue, 
the consumer will instantly crash again, and you create an infinite "Poison Message" 
loop that spikes your CPU to 100%.

2. The Solution
Dead Letter Exchange (DLX): We configure our main RabbitMQ queue so that when a message is explicitly rejected (requeue=False), 
it isn't deleted. Instead, RabbitMQ routes it to a special "quarantine" queue (the DLQ) for debugging.

Bounded Retries: We use Redis to count how many times an event_id has failed. If it fails 1, 2, or 3 times, we requeue=True. On the 4th failure, we requeue=False, letting RabbitMQ sweep it safely into the DLQ.


When a server crashes and comes back online, if 10,000 disconnected clients all try to 
reconnect at the exact same millisecond, they will accidentally trigger a 
Distributed Denial of Service (DDoS) attack on their own server (known as the "Thundering Herd" problem).


2. The Distributed-Systems Concept: Graceful Degradation & Eventual Consistency
Graceful Degradation: If a non-critical component (like Redis presence) fails, the core system (saving messages) should still work.

Eventual Consistency: If RabbitMQ fails, the message might be delayed, 
but the Transactional Outbox pattern guarantees it will eventually be delivered once RabbitMQ returns.
